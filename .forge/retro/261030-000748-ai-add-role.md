# 2026-10-30 — 설명 한두 줄로 AI가 역할 하나를 만들어 팀 편집 화면에 추가

## 계획 대비 실제
- 계획대로 된 것:
  - S3(편집 화면 UI, en/ko 문구)와 S4(e2e "proposes one role from a description")는 계획대로 끝났다.
  - TDD로 진행해 `tests/role-proposal.test.ts` 10개가 실패하다가 통과했다.
  - 실제 데몬 e2e는 6/6 통과했다(34.6초). 실제 provider가 역할 JSON을 제대로 돌려줬고, 기존 역할과 이름이 겹치지 않았고, 모델 검증 오류가 없었다. Apply 때 역할 제안 planner도 기존 정리 규칙으로 보관됐다.
  - 사용자가 앱에서 UAT로 확인했다.
- 달라진 점:
  - S1·S2: 팀 제안 코드와 똑같은 부분이 생겨서 공통 함수로 뽑았다.
    - 역할 JSON 스키마, 모델 목록 줄, JSON 추출: `ROLE_EXAMPLE`·`modelLines`·`jsonIn`
    - planner를 기다리고 오류를 처리하는 부분: `plannerAnswer`
    - 기존 `tests/proposal.test.ts`가 그대로 통과해 동작이 바뀌지 않았음을 확인했다.
  - S5: OVERVIEW의 "provider로 보내는 데이터" 문장을 고쳤다. 역할 설명과 기존 역할 이름·workspace·폴더도 보내게 됐기 때문이다. 이 문장은 레지스트리 리뷰가 보는 데이터 접근 설명이다.
  - DoD 5(`paseo plugin reload`)는 쓸모가 없었다. 설치된 플러그인이 GitHub에서 받은 버전(`git:gyuha/paseo-agent-team`)이라 reload해도 작업 폴더의 변경이 반영되지 않는다. 사용자가 직접 작업 폴더 설치로 바꾼 뒤에야 UAT를 할 수 있었다.

## 배운 점
- 다음엔 다르게:
  - 앱 UAT가 필요한 계획에서는, DoD를 쓰기 전에 `paseo plugin ls`로 설치된 플러그인의 출처(SOURCE)를 확인한다.
    - 출처가 Git이나 레지스트리면 "작업 폴더 설치로 바꾸고, 끝나면 되돌린다"를 UAT 준비 단계로 계획에 넣는다. 배포 스킬이 쓰는 별도 ID(`--id`) 방식은 같은 화면이 두 번 등록되므로 UAT에는 쓰지 않는다.
  - planner처럼 "에이전트를 띄우고 마지막 메시지를 파싱하는" 기능을 하나 더 만들 때는, 처음부터 기존 기능과 공통 함수를 나눠 쓰도록 작업 단위를 잡는다.
  - 새 기능이 provider로 보내는 데이터를 늘리면, OVERVIEW의 데이터 접근 문장을 같은 작업에서 고치는 일을 DoD에 넣는다.
